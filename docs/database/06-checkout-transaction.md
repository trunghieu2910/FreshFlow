# FF-06-03-2 — Checkout transaction and create order API

`POST /api/v1/orders` accepts `X-User-Id` (the project's current mock customer identity), `Idempotency-Key` and a JSON command with `storeId`, `items`, `address` and `paymentMethod`. Each item has `productId`, `variantId` and a positive `quantity`. Supported payment methods are `ONLINE_MOCK`, `CASH_ON_DELIVERY` and `BANK_TRANSFER_ON_DELIVERY`. The request has no trusted price, fee, discount or total fields; extra client totals are ignored. Until delivery pricing is configured, the server applies a zero delivery fee and zero discount.

The checkout service runs one PostgreSQL transaction at `READ COMMITTED`. It claims the `(customer, idempotency key)` record, then locks catalog rows while checking active Store, Category, Product and Variant, including Store ownership. It reserves each variant at the default active inventory location. `MADE_TO_ORDER` uses a date-scoped capacity record, initialized from `daily_capacity_default` when absent; `LIMITED_STOCK` requires an existing stock record. Conditional `UPDATE` statements increment `reserved_quantity` and `version` only when enough capacity or stock remains. Variant IDs are processed in ascending order to reduce deadlock risk.

The same transaction persists the Order and immutable item/address snapshots, a pending payment attempt, audit events and the idempotency response body. Any failed item or write rolls all of these back, including earlier reservations. A retry with the same key and body returns the original response; reusing a key with a different body returns `409`. Database uniqueness on `(user_id, idempotency_key)` serializes concurrent retries. Invalid command fields return `400`; unavailable, inactive or cross-Store items and exhausted inventory return `409`. A successful creation returns `201` with server-calculated totals.

Initial state follows the approved acceptance policy: one manual variant makes the whole Order `AWAITING_MERCHANT_CONFIRMATION`; otherwise online orders start at `AWAITING_PAYMENT` and delivery-payment orders at `PROCESSING`. The order number is generated on the server. The six address columns were added in Flyway V8 and remain nullable for legacy demo orders from V6.

Reservation release on rejection/cancellation and a dedicated concurrent checkout race test belong to the inventory lifecycle follow-up. Until release is implemented, merchant rejection of a newly reserved order does not free its capacity or stock. Customer identity still uses the existing `X-User-Id` mock header; authentication integration will replace it.
